# CLAUDE.md

Правила работы Claude в этом проекте. Код пишет Claude, пользователь принимает
результат и проводит ревью. Договорённости команды (ветки, коммиты, PR, DoD,
архитектура) описаны в [CONTRIBUTING.md](CONTRIBUTING.md) и обязательны.
Если два документа противоречат друг другу, прав CONTRIBUTING.md.

## Скиллы

Скиллы лежат в `.agents/skills/`. Вызывай их до работы, а не после.

| Скилл                    | Когда вызывать                                                     |
| ------------------------ | ------------------------------------------------------------------ |
| `feature-sliced-design`  | Перед созданием любого файла: слой, слайс, сегмент, public API, @x |
| `antd`                   | Перед написанием или правкой любого компонента Ant Design          |
| `requesting-code-review` | Когда фича готова и все проверки зелёные (шаг 7 процесса ниже)     |

Правила скиллов дополняют CONTRIBUTING.md, а не заменяют его. Если скилл
предлагает то, что нарушает CONTRIBUTING.md (например, обёртку над компонентом
antd в `shared/ui`), действует CONTRIBUTING.md.

## Процесс реализации фичи (TDD)

Порядок строгий. Шаги не пропускать и не переставлять.

1. **Проектирование.** Вызвать `feature-sliced-design`, определить слой, слайс
   и сегменты. Если в фиче есть UI, вызвать `antd` и свериться с API
   компонентов. Коротко описать план и дождаться согласия, пока код не написан.
2. **Red.** Написать тесты до кода фичи (Jest + React Testing Library, запросы
   к API через MSW). Тесты описывают поведение пользователя, а не реализацию.
3. **Проверка красного.** Запустить `pnpm test` и убедиться, что новые тесты
   падают, причём по правильной причине (нет реализации, а не опечатка в
   импорте). Тест, который не падал, ничего не доказывает.
4. **Green.** Написать минимальный код, который проходит тесты. Запустить
   `pnpm test`, все тесты должны быть зелёными.
5. **Refactor.** Убрать дублирование, поправить нейминг. Тесты остаются
   зелёными.
6. **Полная проверка:**
   ```bash
   pnpm lint
   pnpm format:check
   pnpm test
   pnpm build
   ```
   Пока хоть что-то красное, дальше не идти. Чинить причину, а не отключать
   правило или тест.
7. **Code review.** Вызвать `requesting-code-review` на весь diff фичи.
   Замечания уровня Critical и Important исправить и повторить шаг 6. Minor
   исправить или явно объяснить, почему нет.
8. **Коммит и PR** (см. ниже).

Баги чинятся так же: сначала падающий тест, воспроизводящий баг, потом
исправление.

## Pre-commit (Husky)

Перед каждым коммитом хук автоматически запускает линтер, проверку
форматирования и юнит-тесты. Обходить хук нельзя: `--no-verify` запрещён.
Если хук упал, чинить причину и коммитить заново.

## Коммиты и Pull Request

- Формат ветки, коммита и заголовка PR берётся из CONTRIBUTING.md
  (разделы 4-6). Ключ задачи `[TB-N]` обязателен.
- Коммитить можно только после зелёных проверок и code review. `git add`
  только конкретных файлов, без `git add .` и `-A`.
- В сообщениях коммитов и описаниях PR не упоминать Claude и не указывать, что
  текст писал ИИ: никаких `Co-Authored-By: Claude` и `Generated with Claude Code`.
- Форматирование отдельным коммитом, если оно затрагивает много строк.
- Один PR, одна задача. Если diff больше ~400 строк, остановиться и
  предложить декомпозицию.
- Перед `git push` и созданием PR показать пользователю итог: что сделано,
  результаты проверок, замечания code review. Пушить и создавать PR только
  после его подтверждения.
- Описание PR подробное и написано по смыслу: что сделано и зачем, как
  проверить, чеклист из `.github/pull_request_template.md`. Пустые заглушки и
  HTML-комментарии из шаблона не оставлять. Секции без содержания (ссылка на
  Jira, если задачи нет, скриншоты без UI) удалять.
- Мержит ревьюер, не Claude.
