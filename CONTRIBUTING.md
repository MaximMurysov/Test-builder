# Правила разработки

Внутренний документ команды. Всё, о чём мы договорились, зафиксировано здесь.
Если договорённости нет в этом файле — её не существует.

## 1. Окружение

| Инструмент | Версия               |
| ---------- | -------------------- |
| Node.js    | 24.11.1 (минимум 22) |
| pnpm       | 11.9.0               |

Пакетный менеджер — **только pnpm**. В `package.json` прописан `packageManager`,
поэтому npm и yarn будут падать с ошибкой. Это специально: два лок-файла в одном
репозитории приводят к тому, что у разных людей ставятся разные версии пакетов.

## 2. Запуск

```bash
pnpm install       # установить зависимости
pnpm dev           # дев-сервер с горячей перезагрузкой
pnpm build         # продакшен-сборка (проверка типов + сборка)
pnpm lint          # проверка ESLint
pnpm format        # отформатировать код Prettier
pnpm format:check  # проверить форматирование, ничего не меняя
```

## 3. Архитектура

Проект построен по методологии **Feature-Sliced Design** — https://feature-sliced.design

### Слои

Сверху вниз, в порядке убывания ответственности:

```
app       — инициализация: провайдеры, роутер, глобальные стили
pages     — страницы приложения
widgets   — самостоятельные блоки страницы
features  — действия пользователя, несущие бизнес-ценность
entities  — бизнес-сущности предметной области
shared    — переиспользуемый код без привязки к бизнес-логике

P.S.  Правила слоёв и public API теперь проверяются автоматически через eslint-plugin-boundaries, нарушение валит pnpm lint
```

### Правило импортов

**Слой может импортировать только строго нижележащие слои.**
`features` знает про `entities` и `shared`, но `entities` ничего не знает
про `features`. Импорт вверх или вбок запрещён.

**Слайсы внутри одного слоя не импортируют друг друга.**
`entities/user` не может обращаться к `entities/product`. Если две сущности
связаны — связь реализуется на слое выше.

### Public API

Каждый слайс — чёрный ящик. Наружу он отдаёт только то, что явно
экспортирует из своего `index.ts`. Внутренние сегменты (`ui/`, `model/`,
`lib/`, `api/`) — приватные.

```ts
// ✅ правильно — импорт до уровня слайса
import { UserCard } from '@/entities/user';

// ❌ неправильно — лезем во внутренности
import { UserCard } from '@/entities/user/ui/UserCard';
```

`shared` — исключение: у него нет общего `index.ts` в корне, импортируем
посегментно (`@/shared/ui`, `@/shared/lib`). Один баррель на весь `shared`
ломает tree-shaking и порождает циклические импорты.

В `index.ts` **не используем `export *`** — перечисляем публичное явно.
`export *` делает публичным любой новый внутренний хелпер, и мы об этом
не узнаем.

В проекте включён `verbatimModuleSyntax`, поэтому типы реэкспортируются
только через `export type`:

```ts
export { UserCard } from './ui/UserCard';
export type { User } from './model/types';
```

### Алиасы

Относительные пути вида `../../../shared/ui` запрещены. Используем `@/`:

```ts
import { Button } from '@/shared/ui';
```

Алиас настроен в двух местах — `tsconfig.app.json` (`paths`) и
`vite.config.ts` (`resolve.alias`). При изменении правь оба: TypeScript
отвечает за типы и подсказки IDE, Vite — за реальную сборку, и друг о друге
они не знают.

### Стили

UI-библиотека Material UI, стилизация через sx и styled, CSS Modules не используем.

Компоненты MUI не оборачиваем один в один, shared/ui только для того, чего в MUI нет

## 4. Ветки

```
<тип>/<ключ задачи>-<краткое описание латиницей>
```

```
feature/TB-12-fsd-skeleton
fix/TB-31-editor-crash-on-empty-state
refactor/TB-40-extract-shared-ui
chore/TB-5-contributing
docs/TB-22-readme
```

- Ветка всегда создаётся от свежего `main`
- Прямой push в `main` запрещён
- Ветка живёт не дольше двух дней. Живёт дольше — задача была слишком
  крупной, её надо было декомпозировать

## 5. Коммиты

Формат — [Conventional Commits](https://www.conventionalcommits.org):

```
<тип>(<область>): <что сделано> [<ключ задачи>]
```

**Типы:** `feat`, `fix`, `refactor`, `chore`, `docs`, `test`, `style`, `perf`

**Область** — слой или слайс FSD: `shared/ui`, `entities/user`, `app`.
Может отсутствовать, если изменение общепроектное.

**Описание** — в повелительном наклонении, с маленькой буквы, без точки в конце.

```
feat(shared/ui): add Button component with size variants [TB-12]
fix(entities/user): handle null avatar in UserCard [TB-31]
refactor(pages/editor): extract toolbar into widget [TB-40]
chore: apply prettier formatting
```

Ключ задачи в квадратных скобках обязателен для всех коммитов, относящихся
к задаче: Jira подтягивает по нему коммиты и PR прямо в тикет.

Форматирование выносим отдельным коммитом — иначе перестановка точек с
запятой в трёхстах строках скроет пять строк реальной логики на ревью.

## 6. Pull Request

- **Один PR — одна задача**
- Заголовок PR оформляется как коммит: `feat(shared/ui): add Button component [TB-12]`
- Тело заполняется по шаблону `.github/pull_request_template.md`
- **PR больше ~400 строк диффа возвращается на декомпозицию без ревью.**
  Такой объём невозможно отревьюить внимательно
- После создания PR задача переводится в статус **In Review**
- Мержит ревьюер, не автор

## 7. Definition of Done

Задача переводится в **Done**, только когда выполнены **все** пункты.
Не «в основном готово», не «осталось по мелочи».

- [ ] `pnpm build` проходит без ошибок
- [ ] `pnpm lint` чистый
- [ ] `pnpm format:check` чистый
- [ ] Правила слоёв FSD не нарушены
- [ ] Ветка и коммиты соответствуют разделам 4 и 5
- [ ] PR создан, чеклист заполнен, ревью пройдено, ветка смержена в `main`
- [ ] Критерии приёмки самой задачи выполнены
- [ ] Задача в Jira переведена в Done с комментарием, что сделано

**Критерии приёмки и DoD — разные вещи.** Критерии приёмки свои у каждой
задачи и отвечают на вопрос «сделано ли то, что просили». DoD один на весь
проект и отвечает на вопрос «доведено ли до конца и сделано ли качественно».
Нужны оба.

Пока PR не смержен — задача не Done, даже если код написан идеально.

## 8. Рабочий процесс

1. Взять задачу из спринта, перевести в **In Progress**
2. **В In Progress одновременно висит ровно одна задача**
3. Создать ветку от свежего `main`
4. Сделать работу, коммитить мелкими осмысленными шагами
5. Прогнать `pnpm lint`, `pnpm format:check`, `pnpm build`
6. Открыть PR, перевести задачу в **In Review**
7. Внести правки по ревью, дождаться мержа
8. Пройти по DoD, перевести задачу в **Done** с комментарием

DoD не высечен в камне. Если по ходу проекта поймём, что чего-то не хватает —
обсуждаем на ретро и дописываем. Менять DoD посреди спринта нельзя.
